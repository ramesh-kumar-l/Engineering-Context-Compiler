| 8 | Phase 3 task classification is **rule-based** (weighted keyword/phrase regex per `TaskType`), not model/embedding-based, with **no new dependency**. | Exit criteria only requires "reasonable accuracy on a small labeled test set" — no requirement for ML-grade classification. | 9 | Phase 4 evidence retrieval assigns each item a **basic per-retriever relevance score** (keyword overlap for code/test, recency for git) rather than deferring `relevance` to a placeholder value. | `EvidenceItem.relevance` (Phase 1 schema) is a required 0-1 field, so retrieval can't emit valid items without some number; exit criteria only asks for a "candidate evidence set," not ranking. | Emit a constant placeholder (e.g. always 1.0) — rejected, throws away free signal already available (keyword overlap, commit recency) and would make Phase 5's before/after ranking comparison meaningless. Build full multi-signal ranking now — rejected, that's explicitly Phase 5's exit criteria; would gold-plate Phase 4. | Low — scores are heuristic and not cross-source-comparable yet (a 0.6 code score and a 0.6 git score aren't equivalent); flagged in `active-context.md` for Phase 5 to address. | High — each retriever's scoring is internal to its own module; Phase 5 can replace or wrap it without changing `retrieveEvidence`'s signature. |
| 10 | Git evidence retrieval shells out to the real `git` CLI via `execFileSync` with **array arguments (no shell string interpolation)**, and swallows all failures into an empty result rather than throwing. | Needed commit history per file (Section 19 evidence types include Git); no existing git dependency in the project. `execFileSync(cmd, argsArray)` passes args directly to the process, never through a shell, so a path containing shell metacharacters can't be interpreted as a second command (avoids OWASP command-injection). | A git library (e.g. `simple-git`) — rejected, adds a dependency for functionality the CLI already provides losslessly (no-gold-plating). Building a shell string with interpolated paths — rejected outright as a command-injection risk. Throwing when git is unavailable — rejected, git history is supplementary evidence, not a hard requirement; a non-git target repo should still get code/test evidence. | Low — worst case is missing git evidence, not incorrect evidence; tested against an isolated temp repo so behavior doesn't depend on this project's own history. | High — isolated to `gitEvidenceRetriever.ts`; swappable for a library later without changing its exported function's signature. |

| 11 | Phase 5 ranks evidence with a **static, hand-picked per-source-type authority weight** (`SOURCE_AUTHORITY_WEIGHT`) combined multiplicatively with each item's relevance, plus a small additive specificity bonus for symbol-level matches — rather than a learned/configurable weighting. | Phase 4 flagged that relevance scores aren't comparable across source types (a 0.6 code score and a 0.6 git-recency score aren't the same signal); exit criteria requires ">1 signal" and unit tests against known-good orderings. | A single learned weight (e.g. from user feedback/click data) — rejected, no feedback loop exists yet (that's Phase 16). Normalizing relevance via z-scores per source type — rejected, needs a population of items per source to normalize against, adds complexity with no measured benefit yet. Ranking by relevance alone — rejected outright, that's exactly the gap Phase 4 flagged (a highly-relevant git commit could outrank an authoritative source file). | Low — weights are a static table, easy to inspect/adjust; wrong values degrade ranking quality, not correctness (no item is dropped, only reordered). | High — `SOURCE_AUTHORITY_WEIGHT` and `computeRankScore` are exported separately from `rankEvidence`, so the table can be swapped or made configurable later without changing the ranking function's signature. |

| 12 | Phase 6 estimates token cost with a **char-count heuristic** (~4 chars/token, plus a flat per-item overhead), not a real tokenizer dependency; selection is a **greedy, rank-order fill** (skip an oversized item, keep trying smaller later ones) rather than optimal bin-packing; compression **truncates each item's `symbols` list to 8** rather than summarizing text. | Phase 5's `active-context.md` flagged that Phase 6 needed a token-counting strategy decided up front. Exit criteria requires selecting+compressing ranked evidence into a valid package within a budget, with `excluded` reasons populated. | A real tokenizer (e.g. tiktoken) — rejected, adds a heavy/model-specific dependency for a guard that only needs to be in the right ballpark (no-gold-plating). Optimal knapsack/bin-packing over token costs — rejected, meaningfully more complex for a benefit unmeasured against real evidence volumes; greedy-in-rank-order is simpler, deterministic, and still fills leftover budget with smaller items. LLM-based summarization for compression — rejected outright, adds cost/latency/non-determinism to a step that must run on every compilation. | Low — a wrong token estimate or truncated symbol list degrades context quality, not correctness; no item is silently lost, every exclusion is counted in `excluded`. | High — `estimateTokens`/`estimateItemTokens` (`tokenBudget.ts`) and `compressEvidenceItem` (`contextCompressor.ts`) are isolated, single-purpose exports; a real tokenizer or smarter compression can replace either without changing `compileContext`'s signature. |

| 13 | Phase 7 classifies trust with a **static per-source-type rule table** (`classifyTrust`), not a learned/probabilistic model; provenance is **guaranteed by reconstruction from the item's own fields** when a caller-supplied item lacks it, rather than by rejecting such items; conflicts are detected **structurally** (same subject - path/identifier - with differing `trustLevel`), not by comparing claim content. | Exit criteria: every item has provenance; FACT/DERIVED/INFERENCE/UNKNOWN never blurred; conflicting evidence surfaced, not silently resolved. All three retrievers (Phase 4) already attach `provenance` in practice, but nothing enforced it as an invariant of the compiled package, and no code assigned a `TrustLevel` to an `EvidenceItem` at all before this phase. | A learned/weighted trust score — rejected, no feedback loop exists yet (Phase 16) to train against, same reasoning as Decision #11's authority weights. Rejecting evidence items with no provenance outright — rejected, provenance is missing only for hand-built/legacy items and the item's own `source`/`path`/`identifier` already contain enough information to reconstruct a provenance pointer without fabricating new facts. Semantic/content-based conflict detection (e.g. diffing what two docs/commits actually claim) — rejected outright, no NLP/diff capability exists in ECC; would require a new dependency or model call for a phase that explicitly forbids blurring trust levels via guesswork. | Low — a wrong trust classification affects how much weight a *consumer* gives an item, not correctness of the package itself (nothing is dropped); every classification is deterministic and inspectable. Conflict detection is a strict superset check (adds a `conflicts` field) so it can only surface more, never hide, disagreement. | High — `classifyTrust`, `ensureProvenance`, and `detectConflicts` are exported separately from `attachTrust`/`compileContext`, so the rule table or conflict-grouping key can be swapped later without changing `compileContext`'s signature. |

| 14 | Phase 8's CLI uses a **hand-rolled `parseArgs`** (no yargs/commander dependency), a real **`tsc` build step to `dist/`** (previously `noEmit`-only) with `bin.ecc` pointing at the compiled `dist/cli/index.js`, and is tested by calling its exported `runCli(argv)`/`runContext(...)` functions directly rather than spawning a subprocess. | Exit criteria: `ecc context "<task>"` runs end-to-end against a real repo and prints/saves a valid package, with documented usage. Phase 1 (Decision #6) deliberately deferred both a CLI entry point and any build step to "when the CLI phase needs an executable artifact" — that phase is now. | An arg-parsing library — rejected, one command with three optional flags doesn't justify a dependency (no-gold-plating, same reasoning as Decisions #8/#11). Testing via `child_process.spawn` against the built CLI — rejected as the primary test strategy: it would require running `npm run build` before `npm test` (coupling two scripts that are independently useful) and is slower/flakier than calling the exported functions directly, which already exercises the identical code path (`cli.ts`'s `runCli` is what `index.ts`'s shebang entry calls) — a one-time manual smoke test of the actual built binary was run instead to confirm the shebang and process wiring work. Keeping `tsconfig.json` itself `noEmit: false` — rejected, would slow down `npm run typecheck`'s fast feedback loop and conflate two different concerns (type-checking vs. emitting); a separate `tsconfig.build.json` extending it keeps both fast. | Low — a wrong arg parse or output format is a UX bug, not a correctness one (the underlying package is still validated via `validateContextPackage` before being printed); the build step only adds an artifact, it doesn't change any core module's behavior. | High — `runContext` (the pipeline orchestrator) and `runCli` (argv → pipeline → output) are exported separately from the shebang entry point, so a future MCP/skill surface (Phase 9/10) can call `runContext` directly without touching CLI-specific argv/output code at all. |

| 15 | Phase 9's skill is a **pure documentation artifact** (`skills/ecc-context/SKILL.md`, frontmatter + markdown) with **no executable code and no direct call into `runContext`**, kept in a repo-root `skills/` directory (not `.claude/skills/`) for a consumer to copy/symlink into their own agent's skills directory; verified by a **doc-consistency test** rather than a behavioral one. | Exit criteria: "a skill exists that teaches an agent when/how to invoke ECC, without duplicating existing engineering-methodology skills." Nothing in that criteria requires the skill to be code — it requires an agent to learn correct usage. | A skill that shells out to `runContext`/the CLI itself (e.g. a script invoked as part of skill execution) — rejected, conflates "teaching an agent to use a tool" with "being the tool"; the CLI (Phase 8) already is the callable surface, and MCP (Phase 10) will be the programmatic one — a skill duplicating either would be a third, inconsistent way to invoke the same pipeline. Placing the skill under `.claude/skills/` in this repo — rejected, this repo *builds* ECC, it doesn't consume it; the skill's audience is agents working in *other* repositories that install this package, so it belongs alongside the source as a distributable artifact, not wired into this repo's own Claude Code session. A broad "how to do software engineering" skill — rejected outright, that is explicitly what the exit criteria forbids duplicating; the doc is scoped to CLI invocation + output interpretation only, with an explicit "when NOT to use" section pointing planning/coding/review concerns elsewhere. | Low — a stale or wrong instruction degrades an agent's usage of ECC, it can't corrupt a compiled package (the CLI's own validation, Phase 8, still runs regardless of what an agent does with the output). Mitigated by `test/skill/skillDoc.test.ts` asserting the doc's documented flags/fields match what Phase 8 actually implemented, so a future CLI change that isn't mirrored in the doc fails CI instead of silently going stale. | High — it's a single markdown file with one small test; rewording, relocating, or replacing it (e.g. once Phase 10's MCP tool exists and some guidance should mention both surfaces) touches no other module. |

| 16 | Phase 10's MCP surface uses the **official `@modelcontextprotocol/sdk`** (new runtime dependency), its **high-level `McpServer.registerTool` API** with a zod raw-shape input schema, and **stdio as the transport** (`bin.ecc-mcp` → `dist/mcp/index.js`) — mirroring Phase 8's CLI structure exactly (`tool.ts` schema+handler / `server.ts` registration / `index.ts` shebang entry), calling the same `runContext` orchestrator with no new pipeline logic. | Exit criteria: `compile_engineering_context` exposed as an MCP tool; a real MCP client can call it and get a valid package back. | Hand-rolling the JSON-RPC/MCP wire protocol — rejected outright, that's exactly what the reference SDK exists to avoid reimplementing, and doing so would risk protocol drift from real clients. The low-level `Server` class instead of `McpServer` — rejected, the high-level API already provides declarative tool registration, input validation, and `CallToolResult` framing; no advanced feature (custom request handlers, notifications) is needed yet. SSE/StreamableHTTP as the transport — rejected for now, stdio is what locally-installed MCP tools (Claude Desktop/Code-style configs) expect; HTTP is a hosted/remote-deployment concern out of scope for this exit criteria, revisit only if a remote MCP server is ever required. Reimplementing the pipeline in `src/mcp/tool.ts` instead of calling `runContext` — rejected outright, would create a third divergent invocation path alongside the CLI, the exact duplication concern Decision #15 already flagged and avoided for the skill. | Low — thin wrapper over an already-tested pipeline, no `src/core` changes; the tool handler catches every error and returns `isError: true` instead of throwing, so a bad path or internal validation failure surfaces as a normal MCP tool error rather than killing the server connection (unlike the CLI's process-exit-code model, an MCP server has no equivalent of "exit" — protocol correctness requires the connection to survive a bad call). `@modelcontextprotocol/sdk` is the official reference implementation; `npm audit` reports 0 vulnerabilities. | High — isolated to `src/mcp/`; verified with the SDK's own `Client` class over `InMemoryTransport.createLinkedPair()` (a real MCP client/server pair in-process) plus one manual smoke test spawning the actual built `dist/mcp/index.js` as a subprocess via `StdioClientTransport`, so both the protocol logic and the shipped binary/shebang are confirmed working end-to-end. |

| 17 | Phase 11's `EvaluationEngine` lives in **`src/core/evaluation/`** (pure core - no dependency on `src/cli/`; it re-composes the same five core calls `runContext` does, with a minimal inline `RepositoryRef` instead of importing `resolveRepositoryRef`), with a separate **`src/benchmark/`** thin surface (benchmark task definitions, report formatting, a runnable `npm run benchmark` entry) mirroring the CLI/MCP pattern. The "agent alone" condition is a **simulated naive-agent baseline** (keyword grep over file paths in walk order, reading whole matched files, no ranking/trust/compression) rather than a real second LLM call. Benchmark tasks target **this repo's own real codebase** (dogfooding), not only the tiny test fixture. | Exit criteria: at least one "agent alone vs. agent+ECC" comparison run, with the metrics in [[07-evaluation]] measured, not just defined. `active-context.md` had flagged since Phase 10 that no target repository had been chosen to validate against beyond fixtures. | Invoking a real Claude/LLM API as the "agent alone" condition — rejected for now: would add a network dependency, per-run cost, and non-determinism to a test suite that has been deterministic/offline through Phases 1-10; the naive keyword-grep baseline honestly represents what an agent using only generic file-search tools (no ECC) would produce, which is what Section 43's "strong agent alone" comparison point is measuring against — revisit only if a future phase explicitly needs a live agent-in-the-loop evaluation. Folding evaluation into the CLI as a new subcommand — rejected, keeps the CLI's deliberate single-command scope (Decision #14) intact; evaluation measures ECC, it isn't an agent-facing surface like the CLI/MCP/skill. Running the comparison only against `test/fixtures/sample-repo/` — rejected as the sole benchmark: too small (3 files) for a meaningful recall/irrelevance signal; used for fast deterministic unit tests instead, with the real measured run against this repository's actual `src/` tree recorded in [[07-evaluation]]. | Low — no `src/core` module besides the new `evaluation/` one changed, no new runtime dependency; the one metric that came out unfavorable for ECC in the real run (irrelevant-evidence rate, since ECC intentionally returns supplementary git/test evidence beyond each task's narrow 2-path ground truth) was reported as-is rather than adjusted, since the point of an evaluation harness is measuring honestly, not tuning ground truth to flatter the result. | High — isolated to `src/core/evaluation/` and `src/benchmark/`; `computeConditionMetrics` and `runEvaluation` are exported separately from `runBenchmark.ts`'s entry point, so a future real-agent-in-the-loop condition could be added alongside the naive baseline without changing the metric-scoring function. |
