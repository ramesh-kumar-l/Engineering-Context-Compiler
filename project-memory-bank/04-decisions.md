| 8 | Phase 3 task classification is **rule-based** (weighted keyword/phrase regex per `TaskType`), not model/embedding-based, with **no new dependency**. | Exit criteria only requires "reasonable accuracy on a small labeled test set" — no requirement for ML-grade classification. | 9 | Phase 4 evidence retrieval assigns each item a **basic per-retriever relevance score** (keyword overlap for code/test, recency for git) rather than deferring `relevance` to a placeholder value. | `EvidenceItem.relevance` (Phase 1 schema) is a required 0-1 field, so retrieval can't emit valid items without some number; exit criteria only asks for a "candidate evidence set," not ranking. | Emit a constant placeholder (e.g. always 1.0) — rejected, throws away free signal already available (keyword overlap, commit recency) and would make Phase 5's before/after ranking comparison meaningless. Build full multi-signal ranking now — rejected, that's explicitly Phase 5's exit criteria; would gold-plate Phase 4. | Low — scores are heuristic and not cross-source-comparable yet (a 0.6 code score and a 0.6 git score aren't equivalent); flagged in `active-context.md` for Phase 5 to address. | High — each retriever's scoring is internal to its own module; Phase 5 can replace or wrap it without changing `retrieveEvidence`'s signature. |
| 10 | Git evidence retrieval shells out to the real `git` CLI via `execFileSync` with **array arguments (no shell string interpolation)**, and swallows all failures into an empty result rather than throwing. | Needed commit history per file (Section 19 evidence types include Git); no existing git dependency in the project. `execFileSync(cmd, argsArray)` passes args directly to the process, never through a shell, so a path containing shell metacharacters can't be interpreted as a second command (avoids OWASP command-injection). | A git library (e.g. `simple-git`) — rejected, adds a dependency for functionality the CLI already provides losslessly (no-gold-plating). Building a shell string with interpolated paths — rejected outright as a command-injection risk. Throwing when git is unavailable — rejected, git history is supplementary evidence, not a hard requirement; a non-git target repo should still get code/test evidence. | Low — worst case is missing git evidence, not incorrect evidence; tested against an isolated temp repo so behavior doesn't depend on this project's own history. | High — isolated to `gitEvidenceRetriever.ts`; swappable for a library later without changing its exported function's signature. |

| 11 | Phase 5 ranks evidence with a **static, hand-picked per-source-type authority weight** (`SOURCE_AUTHORITY_WEIGHT`) combined multiplicatively with each item's relevance, plus a small additive specificity bonus for symbol-level matches — rather than a learned/configurable weighting. | Phase 4 flagged that relevance scores aren't comparable across source types (a 0.6 code score and a 0.6 git-recency score aren't the same signal); exit criteria requires ">1 signal" and unit tests against known-good orderings. | A single learned weight (e.g. from user feedback/click data) — rejected, no feedback loop exists yet (that's Phase 16). Normalizing relevance via z-scores per source type — rejected, needs a population of items per source to normalize against, adds complexity with no measured benefit yet. Ranking by relevance alone — rejected outright, that's exactly the gap Phase 4 flagged (a highly-relevant git commit could outrank an authoritative source file). | Low — weights are a static table, easy to inspect/adjust; wrong values degrade ranking quality, not correctness (no item is dropped, only reordered). | High — `SOURCE_AUTHORITY_WEIGHT` and `computeRankScore` are exported separately from `rankEvidence`, so the table can be swapped or made configurable later without changing the ranking function's signature. |

| 12 | Phase 6 estimates token cost with a **char-count heuristic** (~4 chars/token, plus a flat per-item overhead), not a real tokenizer dependency; selection is a **greedy, rank-order fill** (skip an oversized item, keep trying smaller later ones) rather than optimal bin-packing; compression **truncates each item's `symbols` list to 8** rather than summarizing text. | Phase 5's `active-context.md` flagged that Phase 6 needed a token-counting strategy decided up front. Exit criteria requires selecting+compressing ranked evidence into a valid package within a budget, with `excluded` reasons populated. | A real tokenizer (e.g. tiktoken) — rejected, adds a heavy/model-specific dependency for a guard that only needs to be in the right ballpark (no-gold-plating). Optimal knapsack/bin-packing over token costs — rejected, meaningfully more complex for a benefit unmeasured against real evidence volumes; greedy-in-rank-order is simpler, deterministic, and still fills leftover budget with smaller items. LLM-based summarization for compression — rejected outright, adds cost/latency/non-determinism to a step that must run on every compilation. | Low — a wrong token estimate or truncated symbol list degrades context quality, not correctness; no item is silently lost, every exclusion is counted in `excluded`. | High — `estimateTokens`/`estimateItemTokens` (`tokenBudget.ts`) and `compressEvidenceItem` (`contextCompressor.ts`) are isolated, single-purpose exports; a real tokenizer or smarter compression can replace either without changing `compileContext`'s signature. |
